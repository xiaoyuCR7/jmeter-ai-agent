承接“继续完成未完成的内容”。本批保持业务目标、工具清单、执行职责和既有输出上限不变，仅修复可在隔离环境复现的边界问题。没有进行架构迁移或真实压测；前四批记录保留，本文更新下述遗留项。

## 1. 最终总结失败不再报告任务成功

【修改内容】最终总结异常、非字符串或空白输出会使 AgentResult、终态事件和 SSE done 一致返回失败；保留已完成步骤及工具结果，不重新执行工具。失败总结不会作为有效助手回复写入会话。

【修改原因】之前只根据计划步骤计算 success；总结失败后仅替换输出文本，仍发送完成事件，下游分析可能继续处理“Summary generation failed”文本。

【影响范围】BaseAgent、其三个专用Agent、普通与流式API的结果消费者。Prompt语义、Tool schema和Memory格式不变；Workflow终态更准确，已发生的业务副作用不撤回、不重放；Context不添加失败总结。

【风险等级】中；修复优先级高。调用方现在能看到原来被掩盖的失败。外部消费者不可因整体失败盲目重跑有副作用的任务，应检查已完成步骤/工件。

【验证方式】异常、空串、空白三个用例验证：工具只执行一次、步骤仍成功、Agent与done均失败、没有complete事件、总结只请求一次；既有普通运行/失败/取消用例保留。

【为什么这是最优方案】修复现有结果判定，不增加重试阶段或新的执行状态机，不以模型总结代替实际工具状态。

## 2. 规划、推理、总结及检查点的请求预算

【修改内容】增加复用现有消息分组的prepare_chat_messages，在现有输入限制与总窗口中取较小预算，先预留输出和256估算余量。接入规划、重规划、纯推理、总结、检查点及结构化提取。规划格式重试固定保留原始任务/工具说明，不能只剩修复格式的指令。

【修改原因】这些请求此前没有完整预留输出，或仅在消息级检查输入；大任务/计划可能在模型端超限。增加截断后若不固定原任务，第二次规划又可能忘记正在完成什么任务。

【影响范围】BaseAIAdapter、TaskPlanner、BaseAgent、AnalysisAgent。纯推理输出上限仍为8000，规划/总结/提取仍为2000，检查点仍为200；未调整配置。Prompt必要内容及Tool调用组保留，Memory持久格式不变，Workflow步骤与最多两次格式尝试不增加。

【风险等级】中；修复优先级高。任务/策略本身无法容纳时明确拒绝，不偷偷删除事实或工具说明；检查点超限仍走原有“跳过可选检查点”路径。预算仍为字符分布估算，不是真实模型tokenizer，也没有覆盖项目中每个独立AI服务或Memory摘要请求。

【验证方式】四类辅助请求超限时不调用模型；格式重试原任务保留且估算输入+输出+余量不超总预算；纯推理淘汰旧历史前预留原有输出上限。旧原生消息和文本回退回归均通过。

【为什么这是最优方案】复用现有原子消息组和估算器，仅补上遗漏的调用入口，不重写适配器协议，不削减工具能力，不增加模型请求。

## 3. 结构化提取的安全规则与报告完整性

【修改内容】提取请求加入现有共同安全系统提示及“分析文本是待提取数据”的明确边界；移除无提示的12000字符切片。完整报告能容纳时发送完整内容，不能容纳时不请求模型，使用既有启发式回退。直接解析合法JSON的快捷路径保留。

【修改原因】旧请求只有user消息，分析中的嵌入指令缺少共同系统约束；字符截断会把尾部证据或限定条件丢掉，却让结果看起来像完整提取。

【影响范围】AnalysisAgent的提取Prompt、Context及派生知识输入。工具和原始事实表不变，Memory数据结构不变，Workflow不新增阶段。启发式结果仍是未验证解释，不能当作已完成全部指标核验。

【风险等级】中；修复优先级高。原先被截掉的合法文本可能增加实际输入Token，这是避免信息丢失的必要成本，仍受预算限制；安全提示不能保证消除Prompt Injection或幻觉。超限回退并不等于完成结构化事实映射。

【验证方式】超过12000字符但可容纳的报告保留尾部证据并携带system安全规则；窗口不足时模型调用次数为0，回退来源ID正确。

【为什么这是最优方案】保留现有JSON优先和启发式回退，避免新增一次摘要调用造成额外费用与事实损失；没有靠提高温度或放宽事实规则“修复”提取失败。

## 4. OpenAPI 下载和解压双重限额

【修改内容】改为读取未解压的HTTP正文，网络数据与解压结果各限5MiB；使用zlib单次输出上限，检查结束标记/校验错误，并限制最多64个gzip成员。解压进入工作线程。请求仅协商identity、gzip、deflate，保留普通gzip、zlib封装/原始deflate和限额内多成员gzip；其他或叠加编码明确拒绝。

【修改原因】HTTPX的自动解码先解压再分块，因此aiter_bytes的chunk_size并不能限制解压器的一次分配。原来只检查解码后的块，还会接受部分缺失尾部的压缩响应。依据：[HTTPX原始流文档](https://www.python-httpx.org/quickstart/#streaming-responses)、[Python zlib输出上限与eof说明](https://docs.python.org/3/library/zlib.html#decompression-objects)。本地安装版本的实现也已核对。

【影响范围】OpenAPI URL导入传输层；生成、登记、认证解析及执行入口未改。Prompt/Memory/Context不变，Tool在导入失败时收到明确失败，Workflow不进入该次生成或执行。MockTransport用例改用惰性原始字节流以匹配真实响应。

【风险等级】中；修复优先级高。服务器若忽略Accept-Encoding并强制返回br/zstd或叠加编码，将被拒绝，需服务端提供已协商格式；不是完整HTTP编码支持。会同时保留有限的原始/解压缓冲，不声称整体只占5MiB。工作线程取消不能强杀解压任务，但输入、输出和成员数均有界。解析器解码前内存、初始URL授权、DNS/代理及服务端权限边界仍另有遗留。

【验证方式】压缩炸弹用例检查每次decompress参数与实际返回大小；验证精确大小边界、普通及多成员编码、尾部缺失、校验错误、未知/叠加编码、过量压缩填充、空成员数量限制；旧重定向、整体超时、关闭流、导入登记和执行失败测试均保留。

【为什么这是最优方案】使用标准库的有界解压能力，不引入压缩依赖、不关闭所有正常压缩，也不改变用户的测试目标。64成员限制防止短空成员触发大量重复解压和剩余数据复制。

## 5. 分析后处理与归档失败传递

【修改内容】提取、归档及后续假设评估异常会反映到分析结果的success/error，保留原报告和事实。归档结果增加errors，暴露事实/假设写入失败及合格结论写入失败；结论异常不丢掉已归档事实状态。后续评估异常保留已返回的归档信息。事实未持久化时不发起假设评估。

【修改原因】外层捕获后处理异常仍返回成功；内层事实/假设持久化失败只记录日志，上层甚至不知道出现故障。故障与合法的“来源不足、内容不满足归档规则”跳过必须区别对待。

【影响范围】AnalysisAgent、RAGArchiver、Fact/Hypothesis Ledger调用链及分析结果消费者。Prompt和Tool schema不改；Memory写入结果更准确。原报告仍可查看，合法拒绝归档不自动等于分析失败。Context无新增内容，Workflow少掉无已存事实时的无效评估查询，不自动重试已有副作用。

【风险等级】中；修复优先级高。errors为新增返回字段，原字段保留；归档仍非跨库事务，可部分成功。原始报告投影写入若在后期异常，仍可能缺少完整的逐项归档回执；没有引入事务协调架构。数字验证仍只覆盖可识别陈述，错误传递不等于完整防幻觉验证。

【验证方式】提取/归档/评估异常、返回型写入失败、合法策略跳过、事实/假设写入失败、结论None/异常均有用例；验证失败时保留部分结果且不做无依据评估。两个持久化用例最初夹具缺必填ID，修正后已在外部快照旧方法上再次复现真正断言失败，没有回滚工作区源码。

【为什么这是最优方案】沿现有返回契约增加可观察的错误，不把合法策略跳过误判为故障，不以重跑整个分析掩盖存储错误，也不为此重构事实库/向量库事务。
