## 一、逐项修改说明

### 完成任务的登记清理及 SSE 所有者交接保护

**【修改内容】** claim 与 run 统一通过 `_track_owner` 登记当前 Task。首次登记或转移执行所有者时添加完成回调；同一 Task 的重复登记不重复添加回调。回调只在登记表仍指向该 Task 时删除内存项，不执行数据库操作。原 run/abandon 的正常清理继续保留。

**【修改原因】** 原登记表持有 Task 的强引用。如果 claim 后请求返回、异常退出或被取消，却未进入 run/abandon，已结束的 Task 仍被保留；未被消费的 SSE 响应也能复现。Task 可能携带异常及上下文，反复发生会积累内存引用，且 start 会误认为仍有活跃请求。原读取逻辑已经将这种回执显示为 unknown，本批不是修复数据库去重失效。

**【影响范围】** 仅回执服务的进程内 Task 生命周期。SSE 执行任务可能从原请求 Task 接管所有权，因此完成回调必须比较 Task 身份，避免旧请求结束时清除仍运行的执行任务。数据库回执、请求标识、参数指纹、owner 隔离、阶段信息及防重复规则不变；不改表结构、配置或第三方依赖。

**【风险等级】** 低；优先级中。主要回归风险是所有者交接时误删活跃任务，已用受控事件测试。清理在 asyncio 分发完成回调时发生，不承诺 Task 刚变为 done 的同一瞬间即已清理。没有自动删除持久回执、自动重试或接管未知结果。

**【验证方式】** 扩展已有用例，分别覆盖正常返回、异常、取消三种结束路径；直接读取临时数据库，确认内存清理后数据库仍保留原 running/accepted 记录，查询显示 unknown，服务重新 start 后相同标识仍不能重新取得执行权。另覆盖未消费 SSE 返回 409 且不启动分析，以及旧请求完成后新 runner 仍保持 running、可成功保存结果。正常 HTTP/SSE、取消、存储失败、停机和重复请求也通过既有全量回归。

**【为什么这是最优方案】** 在本次批准范围内，任务完成回调直接匹配资源生命周期，只需一个小方法和两处调用替换。相比定时扫描、TTL、弱引用代替所有权或修改数据库状态，不需要新后台任务、策略配置或恢复协议；也保留了对实际运行 Task 的强引用和明确的所有权判断。
