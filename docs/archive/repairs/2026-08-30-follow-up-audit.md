# Agent 项目后续缺陷复扫与修复报告

日期：2026-08-30。范围：在既有跨进程协调修复后继续检查并修复可复现缺陷；保持 Agent 业务目标、产品逻辑、Prompt、Tool Schema、Memory 与前端协议不变。按用户决定，本批不实施平台/JMeter 进程隔离、执行接管、自动恢复或默认多 worker。

后续状态：本报告 9.1 的 CSV 上传限制与 9.2 的弃用迁移已在[安全与性能后续修复报告](2026-08-30-security-performance-continuation.md)完成；9.3 继续保持安全拒绝并说明原因。

## 1. WebSocket 并发订阅恢复与生命周期重启

- **【修改内容】** 为 worker 级事件总线订阅增加独立异步锁和已订阅集合；首个订阅失败时，后续并发连接可重新建立跨 worker 订阅。停止时统一取消并回收心跳任务、清理订阅状态；再次启动时重置 shutdown event。
- **【修改原因】** 原连接锁只保护本地连接表。首个连接已登记、但事件总线订阅失败时，并发进入的第二个连接会误以为无需订阅；同时 `stop()` 后 shutdown event 永久置位，使重启后的后台清理任务立即退出。
- **【影响范围】** `WSManager` 的内部并发控制和启停生命周期。WebSocket 路径、消息格式、ACL、Prompt、Tool、Memory、Workflow 与 Context 不变。
- **【风险等级】** 高。前者会造成跨 worker 进度永久静默丢失，后者会使同进程应用重启后的订阅清理与心跳失效。
- **【验证方式】** 新增并发失败恢复和 stop/start 两项回归测试；修复前分别稳定失败，修复后均通过，并纳入完整回归。
- **【为什么这是最优方案】** 只在 worker 级订阅边界串行化状态转换，不扩大现有本地连接锁的持有时间，也不改变事件协议或引入新中间件。

## 2. ExecutionLifecycle 同进程重启

- **【修改内容】** 新增显式 `start()`：仅在没有遗留任务、执行器和 prepared 状态时重新开放生命周期；应用 lifespan 启动时调用该方法。
- **【修改原因】** `shutdown()` 会永久设置 `_closed=True`，而其他应用服务支持 lifespan 重启。测试客户端、热重载或嵌入式宿主在同一进程第二次启动后，所有执行都会被错误拒绝。
- **【影响范围】** execution lifecycle 与应用启动顺序。Prompt、Tool Schema、Memory、Workflow 步骤和执行业务状态不变；`main.py` 仅新增一次显式启动调用。
- **【风险等级】** 高。若静默清除仍在运行的任务会产生重复执行，因此 `start()` 对非干净状态 fail closed。
- **【验证方式】** 新增 shutdown 后干净重启测试，并执行 lifespan 回归；完整后端回归通过。
- **【为什么这是最优方案】** 不重建全局服务对象，不改变调用者或执行状态机，只补齐与现有 shutdown 对称的生命周期入口，并保留遗留状态保护。

## 3. OpenAPI 导入后的项目重命名并发版本同步

- **【修改内容】** 项目重命名改为深复制缓存对象并通过统一 `persist_project(..., create=False)` CAS 路径写入，同时同步最新 `storage_version`。
- **【修改原因】** 原路径直接调用 DB 更新后只修改缓存名称，没有更新缓存版本，也绕过陈旧写保护。下一次正常项目更新可能无故 409，或在并发下覆盖新值。
- **【影响范围】** OpenAPI 导入成功后的可选项目名更新。生成 JMX、执行开关、Prompt、Tool、Memory、Workflow 与 API 响应结构不变。
- **【风险等级】** 高。属于隐蔽的数据一致性问题，通常延迟到下一次写入才暴露。
- **【验证方式】** 新增缓存版本与数据库版本一致测试，并继续使用该缓存执行下一次 CAS 更新；修复前复现版本不一致，修复后通过。
- **【为什么这是最优方案】** 复用已经验证的单一持久化边界，不增加第二套版本同步逻辑，也不需要改变数据库模型。

## 4. OpenAPI 基线导入失败回滚

- **【修改内容】** 记录本次是否新建项目和计划；在保存 JMX 或登记计划失败时，精确删除本次生成的文件、空目录、缓存记录和数据库项目。清理异常只追加通用警告，不覆盖原始失败原因。执行阶段失败仍保留项目和结果供诊断。
- **【修改原因】** 原导入先创建项目，再生成/登记计划；中间失败会返回失败结果，却留下不可用项目、孤立文件或脏缓存。
- **【影响范围】** 仅新项目的基线构建失败路径。成功路径和执行失败保留语义不变；Prompt、Tool、Memory、Workflow 与 Context 不变。
- **【风险等级】** 高。残留对象会污染项目列表，并可能让重试命中错误状态。
- **【验证方式】** 分别注入 JMX 保存失败和计划登记失败，两项测试验证项目、计划与文件全部回滚；修复前均留下项目，修复后通过。
- **【为什么这是最优方案】** 回滚范围只覆盖本次尚未形成可用基线的资源；不引入跨执行大事务，也不删除已进入执行阶段的诊断数据。

## 5. WebSocket 订阅 TTL 自愈

- **【修改内容】** 事件总线 `touch()` 接收当前本地 execution ID 快照，在一个短事务内刷新已有订阅，并为仍有本地连接但已过期/丢失的行重新登记；不会删除调用时未列出的其他订阅。
- **【修改原因】** 数据库短时不可用超过 TTL 后，协调清理会删除订阅行。原心跳只更新已存在行，本地连接仍在但远端发布者永远看不到该 worker。
- **【影响范围】** 跨 worker WebSocket 心跳。Token 仍不落库，ACL 仍在发送前复核；Prompt、Tool、Memory、Workflow、Context 和消息格式不变。
- **【风险等级】** 中。影响遥测可达性，不改变数据库中的最终执行状态。
- **【验证方式】** 新增“删除订阅行后由活跃本地连接重建”测试，并通过 SQLite 3.53.4/WAL 协调验证路径执行。
- **【为什么这是最优方案】** 利用现有心跳自愈，不增加独立扫描任务；事务只处理本 worker 当前连接的有界 ID 集合，并避免删除竞态。

## 6. RAG 管理 API 阻塞事件循环

- **【修改内容】** 将统计、单文档读取/删除、模块枚举、历史、版本比较和手工归档中的同步 LanceDB、embedding 与文件操作移到 `asyncio.to_thread`；模块枚举和双版本比较各自合并为一次线程切换。
- **【修改原因】** 这些 async route 直接执行同步存储和 embedding 操作，会阻塞整个事件循环，使无关请求、WebSocket 和 SSE 同时变慢。
- **【影响范围】** RAG 管理 API 的调度方式。检索参数、结果排序、文档内容、RAG Prompt、Memory 选择规则、Workflow 与 Context 内容不变。
- **【风险等级】** 中。高延迟 embedding 或大表扫描时影响会放大为全局响应抖动。
- **【验证方式】** 新增线程 ID 回归测试覆盖 stats/get/delete/modules/history/compare/add，确认阻塞调用不在事件循环线程执行；相关 RAG 测试和完整回归通过。
- **【为什么这是最优方案】** 沿用项目已有的 `to_thread` 模式，不更换存储驱动、不增加队列，并减少不必要的跨线程往返。

## 7. Windows 真实子进程测试的瞬时文件读取失败

- **【修改内容】** 测试等待器在原有 20 秒期限内对 `FileNotFoundError` 和 `PermissionError` 重试；不吞掉 JSON 错误、子进程失败或业务断言。
- **【修改原因】** 子进程原子替换响应文件后，Windows 可能短暂拒绝父进程第一次 open。完整回归曾因此失败一次，而相同业务用例随即通过，属于测试同步假设错误。
- **【影响范围】** 仅 `test_schedule_dispatch.py` 的真实 OS 子进程测试辅助函数；生产代码、跨进程协议、Prompt、Tool、Memory、Workflow 和 Context 均不变。
- **【风险等级】** 低。若无限重试会掩盖错误，因此保留原有总超时，并在超时后报告最后一次读取异常。
- **【验证方式】** 目标真实双进程用例连续 3 次通过，随后完整后端回归通过。
- **【为什么这是最优方案】** 修复测试的跨平台可观察性，不针对测试修改生产代码，也不弱化业务断言。

## 9. 发现但未直接实施的架构项

### 9.1 CSV 上传缺少明确大小上限

- **问题与风险：** `data_routes.py` 使用 `await file.read()` 一次性读取上传内容。单个超大 multipart 请求可能占满进程内存；仅依赖反向代理限制也会让直接部署行为不一致。优先级：**高**。
- **推荐方案：** 新增显式、可配置的上传字节上限，按块读取到 `SpooledTemporaryFile` 或有界缓冲区，超限返回 413；同时在部署文档给出代理层相同或更小的限制。
- **为什么未直接修改：** 默认上限、现有大数据集兼容性和 API 错误契约属于产品/部署决策。擅自选择数值可能破坏现有用户流程。

### 9.2 全量时区感知时间迁移

- **问题与风险：** 当前应用内仍有 20 处 `datetime.utcnow()`；Python 已弃用该 API。直接替换为 timezone-aware datetime 可能与现有 SQLite naive 字段、JWT/session 比较和序列化契约冲突。优先级：**中**。
- **推荐方案：** 先定义数据库与 API 的统一 UTC 契约，再按认证、调度、通知、业务模型分批迁移并加入旧数据兼容测试；同时评估 `python-jose` 升级或替代版本。
- **为什么未直接修改：** 这是跨存储和认证边界迁移，不适合在缺陷修复批次做机械替换。

### 9.3 macOS/BSD 协调模式兼容性

- **问题与风险：** 当前启动锁实现有 Windows 与 Linux 路径；协调模式对 macOS/BSD 明确 fail closed。默认单进程使用不受影响，但开源用户不能据此认为可选协调能力已覆盖全部桌面系统。优先级：**中**。
- **推荐方案：** 将“平台隔离”和“本地协调锁”分开处理；后续只扩展并实测 POSIX `flock`/本地文件系统判定，不引入 cgroup、Windows Job 或 JMeter 隔离。
- **为什么未直接修改：** 需要真实平台与文件系统验证；本批遵循用户决定，不以未经实测的通用 POSIX 声明代替证据。

### 9.4 既有延期边界

平台/JMeter 进程隔离、执行停止证明、跨进程执行接管、自动恢复和默认多 worker 继续延期。本批没有通过旁路改变这些架构决定。
