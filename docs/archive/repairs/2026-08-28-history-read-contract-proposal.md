## 二、三个方案与推荐

| 方案 | 收益 | 代价 | 建议 |
|---|---|---|---|
| **A. 仅登记分析严格读取，故障终止** | 不将账本故障当作空历史；覆盖准备及评估链；旧入口保持兼容 | 存储短暂故障时这次登记分析失败；评估晚期失败可能已有部分持久化 | **推荐**。改动集中，无新表、队列或依赖；与现有上下文准备失败停止的规则一致 |
| B. 明确降级后继续只分析本次Fact | 存储故障期间仍能提供部分报告 | 必须新增降级状态、Prompt约束和归档策略，防止不完整报告污染长期知识；UI也要持续展示降级 | 本轮不推荐，需要额外确认“降级报告能否归档/评估”等业务语义 |
| C. 全项目读取API统一返回结果对象 | 所有消费者都能区分成功/无数据/故障 | 涉及旧分析、管理API、工具和更多调用方；迁移与兼容成本大 | 暂缓，不适合此次最小变更 |

不增加自动重试作为第四种隐式方案。尤其在归档或假设状态已提交之后，不应为读取失败重新运行整个分析。

## 三、方案A的具体契约

### 1. 严格模式的启用范围

只由已登记分析的`run_analysis`内部编排显式启用；HTTP与SSE共用。用户文本、LLM输出、请求JSON不能切换该策略。

建议给必要账本方法添加可选的关键字严格读取参数，默认保持旧行为；仅在登记流程中传递。不使用跨请求全局开关，不新增环境变量，不修改数据库结构。直接`analyze_with_rag`、旧通用Agent、管理API及手工调用继续使用原默认契约。

调用链需要同步覆盖：

```text
登记分析
  ├─ 准备历史：Fact.get_facts_for_module_version → Hypothesis.list_for_module
  └─ 归档后评估：evaluate_module_hypotheses
        → list_for_module
        → evaluate_against_facts
            → get当前假设
            → Fact.load新证据/旧证据
            → 原条件更新
            → get更新后状态或并发冲突后的状态
```

严格参数必须传到最后一次读回，不能仅在最外层新增try/except。写入失败原已有失败传播，本批不重写写事务或评估规则。

### 2. 故障、空结果和无效单行必须分开

| 情况 | 严格登记模式的预期行为 |
|---|---|
| 查询成功但无记录/无可用记录 | 正常返回空列表或None，允许现有首次分析和无须评估流程；不证明数据库从未存在记录 |
| limit为0、已知来源execution列表为空 | 保留现有快速返回，不新增健康检查或无意义数据库读取 |
| 账本初始化、建表、连接、SQL执行、游标进入/读取/退出异常 | 抛出具有固定安全描述的`LedgerReadError`；不能变为空结果，也不能返回故障前读取的部分历史 |
| 参数校验失败 | 保留参数错误，不转换成“无历史”，也不归类为存储不可用 |
| 单行JSON/模型损坏、Fact身份不匹配 | 保留已有跳过/None逻辑，不能让一条坏记录阻断全部历史 |
| 历史JTL缺失、已知哈希不一致或原有单行校验捕获的OSError | 继续按已有不可用证据规则跳过；本批严格的是账本读取，不声称区分了所有文件系统故障 |
| Task取消、主动取消、SSE关闭 | 沿用现有取消路径，不能包装为LedgerReadError或触发重试；后台线程的名额仍遵守第十三批规则 |

只在既有查询实际触达的范围内发现故障；不额外扫描全表，不保证发现限额之外的坏记录。避免用“无可用历史”推导“系统里绝不存在历史”。

### 3. 准备阶段失败

当前Fact已经计算成功，但账本读取失败时：

- 停止本次编排，不进入模型循环、结构化提取、归档或假设评估。
- 保留可用的本次Fact作为诊断数据，不将“已计算”描述为“已归档”。
- 返回原失败封装，建议`analysis.phase=history`、`analysis.error_code=ledger_read_failed`。不附加伪造的历史数量0或`history_found=false`来表示存储故障。
- 客户端只看到固定安全错误信息，不暴露数据库路径、SQL、连接参数或底层异常文本。受控服务日志可保留错误类别和阶段以便排查。
- Session与分析名额按现有finally回收；实际同步任务未结束时仍保留draining名额。

该分支不产生后续模型Token；本次Fact计算成本已发生，不宣称零成本失败。

### 4. 归档后的评估读取失败

评估可能发生在Fact、假设、RAG结论已经持久化之后，因此不能简单宣称“什么都没发生”：

- 停止后续评估，整体返回`success=false`，建议`analysis.phase=evaluation`、同一`ledger_read_failed`错误码。
- 保留本次报告、Fact、validation、已有archive回执及先前归档错误，不用新读取错误覆盖已记录的部分失败。
- 不删除已经持久化的Fact、假设、RAG或模型阶段会话记忆，不回滚已提交的其他假设状态，不重放分析。
- 明确评估可能部分完成，不能声称所有假设都未改变。更新后的读回失败也可能发生在提交成功之后。
- 本批不提供逐条持久回执、跨库原子性、幂等恢复或补偿任务；这些仍属于后续持久任务架构。

保留既有“同执行不自证、同scope/版本/测试类型、非空样本、保守预测、条件更新”规则。真实无记录仍按现有规则跳过，不因严格模式强制确认/否定假设。

## 五、批准后的验收标准

1. 针对真实读取方法注入初始化、连接、execute、fetch/迭代及游标收尾故障；严格模式抛安全异常，旧默认保持原行为，已读部分历史不得误报成功。
2. 查询成功空数据、limit=0、来源列表为空、损坏JSON、身份不符、失效JTL、旧哈希前缀及跨scope样本仍符合原规则；不增加查询次数。
3. 登记分析Fact历史/假设历史故障：不进入模型/Tool/归档，Fact诊断可保留，错误消息不含注入的敏感标记；HTTP/SSE行为一致。
4. 评估list/get/新旧Fact.load/更新或冲突后读回故障全部能穿透；失败结果保留已有报告与归档回执，且不自动再次写入或重新调用模型。
5. 若前一条假设更新已提交、后一条读取失败，验证部分状态保留而不是伪造全回滚；不得改变假设确认判据。
6. 无故障的完整登记分析及真正首次分析继续成功，旧直接调用、管理调用与原接口测试继续通过。
7. 取消仍传播，Session/分析名额无泄漏；真实哈希线程结束前仍占用名额，不引入新的重复读取或后台任务。
8. 完成后运行隔离后端全量、前端全量、类型检查、构建、源代码差异复核和Prompt比对；只报告新执行的结果，不引用上一批数字作为本批验收。

所有验证使用临时DB/JTL、故障注入和模型替身；不连接真实模型、JMeter、Docker或远程引擎，不修改用户数据。
