## 二、推荐范围与备选方案

| 方案 | 收益 | 代价/限制 | 建议 |
|---|---|---|---|
| A：先支持同一台服务器、本地磁盘的多 worker，分批补齐权限和协调，再开放受限恢复 | 尽量复用当前数据库与部署方式；可以用独立进程和临时文件验证真实竞争 | 不支持多机；SQLite 写入竞争、RAG 写入所有权、事件路由仍需解决；不是改一个 workers 参数 | **推荐作为首版，前提是用户同意此部署范围** |
| B：直接面向多机/多实例，采用共享数据库、任务执行服务及事件传递设施 | 可以统一处理跨机执行权、事件和调度 | 数据库/存储迁移、凭据、部署组件、文件归属和故障模型明显扩大；需要先确定基础设施 | 若目标已经是多机，应直接设计这一方案，不把 SQLite 文件放到网络盘冒充共享数据库 |

SQLite 官方明确 WAL 要求使用同一数据库的进程位于同一主机，不支持网络文件系统；FastAPI 官方也说明多个 worker 的内存通常不共享。[SQLite WAL](https://sqlite.org/wal.html)、[FastAPI 部署概念](https://fastapi.tiangolo.com/deployment/concepts/)。

### 运行时前置风险

本轮只读检查的 D:/python/python.exe 为 **Python 3.13.7 / SQLite 3.50.4**；这不是对生产环境版本的推断。

SQLite 官方披露 WAL-reset 缺陷：受影响版本在多个连接并发写入/检查点的特定竞争下，可能导致数据库损坏；已在 3.51.3 及后续版本修复，也提供 3.50.7、3.44.6 回补。3.50.4 位于官方说明的受影响范围。**这是运行时风险，不是已发现项目数据损坏。** [官方缺陷说明](https://sqlite.org/wal.html#walresetbug)。

启用新增并发能力前，应使用包含修复的运行时，并核对实际部署解释器和 Memory 使用的 SQLite。仅一个 API worker 也可能创建多个数据库连接，不能用减少 worker 数替代修复。本轮不擅自替换全局解释器、升级项目依赖或修改用户数据库 journal 模式。

## 三、建议实施批次与行为契约

### 第一批：项目 ACL，先在现有单 worker 运行方式下完成

**推荐行为，需确认：** 旧项目及系统默认项目显式标为 legacy_shared，保持当前已认证用户的工作区 RBAC 权限；不设为匿名公开，不猜测创建者。新建普通项目默认私有，由创建者的稳定用户 ID 持有。旧项目转私有必须由管理员显式指定 owner/成员，先预览受影响资源再提交，不做无提示批量迁移。

权限取全局角色与项目授权的交集；项目 owner 不得绕过全局角色上限。全局管理员可执行显式、可审计的成员管理，但不因该角色自动读取其他人的私有分析回执。成员移除后，在下一次受保护读取、工具执行、分析阶段和流事件发送前重新检查；已经发送的内容及已经开始的外部操作不能声称被撤回。

**影响范围：** 增加项目访问模式/成员持久化、统一资源授权服务，接入项目及子资源 API、MCP 工具/资源、报告文件、WebSocket、Agent 输入解析、RAG/Memory 和前端列表/操作权限。列表及数量统计先按授权过滤，再分页；不能先返回再隐藏。授权服务不可将失败解释为共享权限。

**Memory/Context 同步处理：** 私有项目上下文必须有可核对来源。不能把来源不明的旧知识自动归到某一私有项目；会话缓存与历史读取要受项目访问变更约束，不能保留已撤销项目内容继续送给模型。对没有项目归属的全局设置、文件和工具，保留既有更严格角色要求并逐项明确边界。

**收益与代价：** 兼容旧项目当前可见性，逐步建立项目隔离；代价是 legacy_shared 项目在显式迁移前仍然共享，不能宣称所有存量数据已私有化。

**风险/优先级：高/高。** 验收覆盖用户隔离、非法资源 ID、列表/报告/MCP/WS 绕过、成员撤销、Memory 历史泄漏、旧项目迁移失败回滚及默认项目兼容。不触碰用户真实数据。

### 第二批：跨进程协调，全部入口验收后才允许多 worker

**推荐行为：** 在共享的协调记录中保存执行者代次和资源所有权，原子领取同 Session、分析名额和定时批次；所有写入核对当前所有者。租约过期仅说明需要核实，不能直接证明旧 worker、线程、JMeter 子进程或远程模型请求已经结束。

先实现协调原语及双进程测试，再逐项接入：

1. Session 互斥必须先于读取/修改该会话历史；分析名额保留到实际同步工作结束。协调器不可用时拒绝新执行，不回退为每 worker 各自放行。
2. 调度以 schedule ID + 计划触发时间原子领取同一批次。执行 stop/cancel 路由到实际拥有者；不能在错误 worker 上返回虚假成功。
3. 权限、项目、执行状态以持久数据为准，处理各 worker 的旧缓存。启动迁移和扫描写入也需单一所有者，不能任由各 worker 并行迁移。
4. 工具确认共享精确参数、提交者、过期时间和一次性决定；跨 worker 必须可读取，但不能在重启后把旧确认当成可复用授权。
5. WebSocket/MCP 所有者及事件交付要明确。首版不承诺把已断开的 SSE 执行流无缝迁移到别的 worker，断线后的状态查询与任务执行权分开处理。
6. 明确 RAG 写入和缓存所有权。不能只让 SQL 更新检查代次，就宣称所有文件、RAG 和外部工具都能拒绝旧执行者写入。

**影响范围：** lifecycle、BaseAgent、AnalysisRuntime、scheduler、execution_lifecycle、Memory、缓存、确认、MCP、WS 及部署脚本。Prompt 内容不需要为协调改写，但授权筛选和历史读取顺序会影响实际输入。

**收益与代价：** 防止 worker 数增加后重复执行或超出资源限制；代价是额外协调查询、心跳/路由成本和故障时更保守的拒绝行为。先采集开销，不预设吞吐提升百分比。

**风险/优先级：高/高。** 独立操作系统进程测试同键竞争、同 Session、调度重复领取、旧执行者迟到写入、暂停但未死亡的 worker、真实线程 draining、确认跨进程、缓存失效和协调存储故障。仅启动两个服务对象不足以验收跨进程能力。

### 第三批：受限自动恢复，不从任意中断点重跑

**推荐行为：** 只对未来显式启用恢复的登记分析请求保存恢复输入；默认不改变现有请求的断线/取消行为。回执原有 request_id 防重复规则继续生效，旧回执缺少输入快照时不可自动恢复。

首版自动恢复的必要条件：

- 旧执行者已经被可靠确认停止；仅心跳超时或 unknown 不足以接管。
- 持久状态能证明尚未进入模型/Tool/归档副作用区；模型开始之前先提交不可重放边界，提交失败不调用模型。
- 输入、执行来源哈希、配置版本以及所需上下文快照完整；恢复时重新校验当前用户活动状态、角色、项目授权和执行来源，不提升为管理员运行。
- 用户取消、预检失败、容量忙碌、已完成或明确失败不进入自动恢复；恢复次数有上限，超过上限转人工核实，不循环重试。

需要恢复的 task/context/会话快照属于新增敏感持久数据：必须明确大小上限、保留/删除周期、加密密钥来源及备份策略，不能把原访问 Token/API Key 写入恢复载荷；这些配置尚未确定时恢复功能保持关闭。旧授权/旧项目可见性不能充当当前授权。

模型已经开始但结果未可靠保存，或归档/评估可能部分提交时，继续保留 unknown/待核实，**不自动重调模型或重放工具**。后续若要恢复这些阶段，另做逐操作幂等及输出检查点方案；确定性 ID 也不能替代跨存储事务和外部调用结果核实。

**影响范围：** 恢复载荷表、后台恢复协调、回执版本/阶段、AnalysisAgent 执行边界、当前授权、Context/Memory 快照、客户端恢复状态。原请求的业务目标不变，但后台继续执行与取消语义必须显式选择。

**收益与代价：** 可恢复可证明安全的准备阶段中断；代价是多存一份受控输入、更多状态检查，且模型开始后的中断仍不能自动完成。首版不包含 JMeter 压测自动重跑，也不保证外部副作用恰好一次。

**风险/优先级：高/中，依赖前两批。** 使用假模型及临时数据库，在保存边界前后注入进程退出，验证安全请求仅有一个执行者；在模型/工具/归档边界退出必须不重放。用户/项目权限撤销、来源变化、配置变化、损坏载荷、次数耗尽均拒绝恢复。
