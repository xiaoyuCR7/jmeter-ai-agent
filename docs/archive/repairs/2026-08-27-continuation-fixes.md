## 逐项修改

### 1. 两条比较链路的数学口径和运行错误

【修改内容】VersionComparator 不再把缺失、非法、NaN/Infinity 指标当零值；新增 unavailable_metrics。零基线或百分比溢出时 delta_pct=null，保留绝对变化和方向；证据不足返回 unknown。RegressionEngine 同步处理无效值与零基线，修正摘要引用不存在的 delta_pct 属性。接口局部数据缺失不再引发比较异常，根因提示排序稳定。

【修改原因】此前 0→2 被报告为增长100%，缺少吞吐量可被判定大幅回退，正常回归/改善摘要也可能直接抛 AttributeError。

【影响范围】insights_engine、regression_engine、比较 API 和 compare_runs Tool 的返回数据。Prompt/Memory 不变；Workflow/Context 获得明确的未知状态。没有新增模型调用，也未改变原有非零基线阈值。

【风险等级】中。delta_pct 现在允许 null、整体结论允许 unknown；外部自建客户端需处理未知值，不能直接进行算术运算。现有前端未直接计算这些字段。

【验证方式】缺失字段、零基线、非有限值、局部接口数据、实际百分比、回归/改善摘要、严格 JSON 序列化测试。

【为什么这是最优方案】在两处现有计算入口修正口径，保留原返回字段并补充必要信息，不迁移历史结果或重建分析体系。

### 2. RAG 过滤、排序、分页和完整版本列表

【修改内容】module/type 和无 embedding 的 hybrid 查询复用已有 _latest_rows，先过滤、排序后截取；JSON 回退采用模块精确匹配，关键词结果在元数据过滤后限量；最新分析同时按模块和类型过滤。版本列表只查询完整 version 列，取消最近200篇文档造成的遗漏。

【修改原因】先限量会丢失最新知识；模块子串匹配混入其他模块；大量不相关命中可挤掉目标作用域；版本数和最新分析可能不完整。

【影响范围】RAG store 及其 Memory/Tool/Context 消费者。Prompt 和 Workflow 步骤不变；不改文档 schema、不生成新 embedding、不改变已有向量查询语义。

【风险等级】中。排序读取全部匹配文档的少量元数据，仍是 O(n)，不是大规模索引优化；JSON 回退的精确匹配与数据库保持一致。

【验证方式】冷启动、精确模块、先过滤后限量、跨类型最新分析、201个版本测试；已有冷启动关键词回退测试原本就通过，没有重复修复该路径。

【为什么这是最优方案】复用现成查询机制，只读取排序/版本所需列，避免加载全部正文或向量来取得元数据。

### 3. 主报告不再把异常模型输出当作结论

【修改内容】ReportAnalysis 增加 analysis_status（completed/invalid/failed）和 evidence_status（unverified）。模型输出必须通过结构校验并包含非空评估/结论；无效输出不进入 key_findings，不复制为“原始结论”。状态由应用设置，模型不能自称已验证。Web 后处理将分析失败写入 report_status/report_error，不改变 JMeter 已完成状态。两个报告页面及 Markdown 导出同步提示事实核验边界。

【修改原因】无效输出此前可变成看似正常的分析，返回失败对象也没有影响报告状态；格式有效并不代表数字或因果结论正确。

【影响范围】Analyzer、schema、Web 后处理、数据库现有 JSON 序列化、两处报告展示和中英文文案。Prompt 内容不改；Tool/Memory 不新增写入，仍只按原逻辑归档原始指标；Workflow 区分执行结果与分析结果。

【风险等级】中。历史分析默认 unverified，未执行批量迁移。结构错误会明确显示不可用，不再展示未采纳的模型原文。

【验证方式】空对象/数组/非JSON/字段类型错误测试、错误报告状态传播、Markdown提示、全量回归、前端类型检查和生产构建。没有进行真实浏览器视觉验收。

【为什么这是最优方案】在已有 schema 和后处理链路增加明确状态，保留所有原分析字段，不用数字正则把整个自然语言报告冒充“已经事实验证”。主链路逐项证据核验仍未完成。

### 4. 分析与健康检查的重试预算

【修改内容】鉴权、配置和格式错误不反复重试；连接错误、超时、408/429/5xx 保留最多3次分析尝试，只在还有下一次时退避。分析和健康检查显式关闭 SDK 内层重试；健康检查增加15秒总等待边界。失败结果和日志保留错误类型，不复制供应商完整错误字符串。失败提示不再建议重新执行压测。

【修改原因】外层与 SDK 重试叠加放大请求数量、延迟和费用；重跑压测不能修复鉴权错误；供应商错误可能带 URL、密钥或请求内容。

【影响范围】Analyzer、四类适配器的 chat、factory.health_check。Prompt 语义/Tool/Memory/Context 不变；Workflow 在不可恢复错误时更早结束。其他 Agent 调用仍保留原 SDK 默认策略，没有声称形成全系统统一预算。

【风险等级】中。严格错误分类不再根据任意异常文本猜测可重试；分析每次仍有120秒等待上限。客户端超时不证明远端供应商已停止计算或计费。

【验证方式】401仅调用一次、瞬时连接错误恢复、真实安装的 OpenAI SDK + HTTPX MockTransport 429 请求计数、健康检查超时取消。无真实模型请求或费用测试。

【为什么这是最优方案】让分析入口持有自己的重试预算，避免嵌套重试；不对有副作用的压测 Tool 增加盲目重试。

### 5. 流式响应和兼容消息回收

【修改内容】OpenAI/DeepSeek/Qwen 的流正常结束、消费者关闭或读取异常时关闭响应；托管生成器负责关闭内部迭代器。DeepSeek/Qwen 文本兼容路径保留工具调用及结果ID的文本表示，避免发送缺失关联字段的 tool role。Anthropic 普通回复合并文本块，不假定第一个块一定是文本；空 OpenAI 文本返回空字符串。

【修改原因】流中断可能遗留连接；兼容适配器丢失原生 Tool 关联信息；多内容块响应不能按第一个文本字段读取。

【影响范围】四类适配器、Tool 结果传递、Context 和流式 Workflow。Memory 原有结构不改，Prompt 不追加新规则。

【风险等级】中。正常内容不主动重试已输出的流，避免重复回答或重复工具请求；真实供应商断网行为仍需验收。

【验证方式】三种兼容适配器 × 正常/显式关闭/异常的9个用例，原生消息和 Memory 往返回归。

【为什么这是最优方案】使用明确的 finally/异步上下文关闭资源，复用已有文本消息转换，不引入新的传输层。

### 6. 缓存适配器的配置失效与关闭

【修改内容】适配器记录在途调用；配置失效先从缓存移除，闲置连接立即关闭，在途连接在最后一次调用退出后关闭。旧适配器不再接受新调用，避免静默继续使用已更换的配置。七处配置路由同步 await invalidate。应用退出关闭所有缓存/退休客户端，无法关闭的实例保留并明确失败。

【修改原因】旧实现仅清空字典，不关闭连接；直接关闭又可能打断正在执行的请求。

【影响范围】BaseAIAdapter、四类 SDK 适配器、Factory、配置 API、应用生命周期。Tool/Memory/Prompt 不改变；若用户在长任务中途修改模型配置，任务下一次模型调用会明确提示配置已变更，需要重新发起，不能悄悄切换身份或密钥。

【风险等级】中。面向当前单 worker/单事件循环部署，不是多进程协调机制。外部直接使用 invalidate 的代码必须改为 await。

【验证方式】正在等待的请求不被关闭、完成后关闭一次、闲置立即回收、旧实例拒绝新请求、退出重复清理不重复关闭、全量 API/Agent 回归。

【为什么这是最优方案】生命周期只落在已有适配器和缓存层，明确连接所有权；不强制中断用户当前请求，也不依赖垃圾回收及时释放连接。

### 7. 应用异常退出与预加载状态

【修改内容】运行期资源采用 AsyncExitStack 登记清理，启动失败、服务异常、某一清理失败仍会继续其他清理；按顺序停止预加载任务、WS、调度、执行生命周期、资源监控和 SDK。embedding 预加载的 loading 标志在取消/异常时复位。

【修改原因】yield 后顺序代码在异常退出时可能不执行；未跟踪的预加载任务可能遗留，取消后 loading=true 会使后续加载一直被跳过。

【影响范围】main.lifespan、RAG embedding 状态、调度/执行/SDK。Prompt/Tool/Memory 内容不改，Workflow 清理更可靠。

【风险等级】中。取消 asyncio.to_thread 的等待不会强杀已进入的模型加载线程；本批不宣称后台原生计算具有可强制终止的沙箱。必须完成真实 embedding 加载/关机验收。

【验证方式】启动阶段异常、服务阶段异常、预加载取消标志复位，以及原执行/取消测试。

【为什么这是最优方案】用标准异步资源栈修复局部所有权，不重建整个任务系统。

### 8. OpenAPI 下载的跳转、大小和时间边界

【修改内容】仅接受无内嵌凭据的 HTTP(S) URL；关闭自动跳转，最多5次同源跳转，跨协议/主机/端口跳转要求用户核对并显式提供最终 URL。流式读取并限制文档正文为5MiB，设置30秒整体下载等待边界；同源跳转后使用最终 URL 解析相对 server 地址。错误输出不带完整请求 URL。

【修改原因】旧代码可自动访问确认范围之外的地址、一次性加载任意大正文，并在错误中泄露查询凭据；相对地址还可能基于错误的初始 URL 解析。

【影响范围】OpenAPI URL 导入/API/Tool/项目生成的相对地址。内网初始目标仍支持；Prompt/Memory 不变，下载失败不进入后续生成/执行。

【风险等级】中至高。跨源 CDN/HTTP→HTTPS 跳转需显式使用最终 URL，超大文档需拆分或另行设计上传预算。此修改不是完整 SSRF 防护：初始目标授权、DNS重绑定、代理、压缩解码和解析器资源预算仍需部署治理。

【验证方式】HTTPX MockTransport 验证跨源跳转只发1次请求、同源跳转保留最终 URL、超限流提前关闭、慢流总超时取消且不暴露查询参数；没有访问任何真实目标。

【为什么这是最优方案】在现有导入入口约束请求，保留内网性能测试能力。流与客户端的关闭方式依据 [HTTPX 异步文档](https://www.python-httpx.org/async/)，跳转由应用显式处理，参见 [HTTPX 跳转文档](https://www.python-httpx.org/quickstart/#redirection-and-history)。
