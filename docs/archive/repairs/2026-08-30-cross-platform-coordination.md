# 非隔离跨进程协调实施报告

日期：2026-08-30。范围：继续已批准的同机、本地 SQLite 协调方案，但按用户决定**不实施 Windows Job、Linux cgroup 或其他 JMeter 进程隔离**。本批没有启用多 worker、自动恢复、真实 JMeter、真实模型或用户数据库迁移，也没有修改业务目标、Prompt 文本、Tool 定义或 Memory 实现。

## 1. 跨 worker 工具确认

- **【修改内容】** 默认单进程路径保持内存确认；显式注入 Coordinator 时，确认请求以稳定用户 ID/代次、精确 Tool 参数指纹和原 operation/claim 持久化。参数使用 JWT_SECRET 域分离派生密钥加密；决定只能 pending→approved/denied→consumed 一次，超时、取消及异常清空密文并转 abandoned。
- **【修改原因】** 原确认存在于单 worker 内存，另一个 worker 无法查看或决定；仅按用户名绑定还会让删除后重建的同名用户继承旧确认。
- **【影响范围】** confirmations、确认 API、确认表和 ToolRegistry 的既有确认边界。Prompt、Tool Schema、Memory、Workflow 语义和 Context 内容不变；协调路径仅增加短轮询，不增加模型调用。
- **【风险等级】** 高。密钥变化会使未决确认不可解密；这是安全失败，不能回退为明文或自动批准。
- **【验证方式】** 先得到功能失败，再通过 23 项确认/权限测试；真实独立 OS 子进程创建、另一个进程决定，验证 SQLite 3.53.4/WAL、一次性消费、跨用户拒绝、删除重建拒绝及数据库中无参数明文。
- **【为什么这是最优方案】** 复用现有主数据库和确认 API，不增加外部队列，不改变 Tool 参数；只在显式协调部署承担持久化成本。

## 2. DB 权威缓存、完整失效和陈旧写保护

- **【修改内容】** 新增事务内递增的全局 business revision；协调模式在 HTTP/Tool/Agent/调度边界按需加载项目、计划、执行的完整分页快照，并用一次替换传播更新和删除。三类业务记录新增隐藏 storage_version，更新采用原子 `WHERE id AND version` CAS；API 响应不输出该字段。显式更新不会在并发删除后重建旧项目。
- **【修改原因】** 各 worker 启动后长期保留旧缓存；旧对象不仅读旧值，还可能覆盖另一个 worker 的新提交或复活已删除记录。
- **【影响范围】** DB 模型/增量迁移、DBStore、SharedStore、project_scope、execution_lifecycle 和项目环境 Tool 的内部持久化。Prompt、Tool 定义、Memory、Context 与业务字段不变；冲突从静默丢数据变为 409/LookupError。
- **【风险等级】** 高。调用方遇到 409 应刷新后由用户重试，不能自动重放整次副作用工作流。
- **【验证方式】** 功能回归先复现旧缓存、丢更新和删除后复活；相关组合 89 项及竞态组合 78 项通过。真实子进程更新项目后，父进程旧缓存只在下一边界刷新，并验证 WAL 和独立 PID。
- **【为什么这是最优方案】** 单个修订号低成本解决读缓存失效，每记录 CAS 精确解决写覆盖；无需移除现有缓存或引入 Redis。

## 3. RAG 写入所有权与回退缓存

- **【修改内容】** 协调模式按规范化 RAG 路径哈希领取唯一写租约，覆盖初始化、JSON 迁移、add/update/delete、零向量后台修复和原子文件替换。JSON fallback 使用文件签名检测其他进程提交并原地刷新本地缓存；LanceDB 读取绕过陈旧对象缓存。
- **【修改原因】** 进程内锁不能阻止两个 worker 对 fallback JSON 执行各自的读改写，也不能保护迁移或后台向量修复。
- **【影响范围】** LanceRAGStore 的存储边界。检索过滤、文档类型、RAG Prompt、归档 Workflow、Memory 与 Context 选择规则不变；忙碌时安全拒绝，不本地降级绕过租约。
- **【风险等级】** 高。协调存储不可用时 RAG 写入会失败；不能为了可用性允许未加锁的并发写。
- **【验证方式】** 107 项 RAG/知识权限测试通过；真实子进程写入后既有父进程 store 读取到双方文档，且共享 DB 为 WAL、PID 独立。
- **【为什么这是最优方案】** 保留 LanceDB/JSON 双后端和现有检索逻辑，只把互斥放在实际写边界，不增加 Token 或模型请求。

## 4. 启动迁移单 owner

- **【修改内容】** SQLite 建表及增量迁移前获取同数据库旁的短期跨进程文件锁。Windows 使用 `msvcrt`，非 Windows 锁路径使用 `flock`；锁由 OS 在进程退出时释放，等待有界，取消与抢锁竞态会排空短调用并立即释放。当前本地磁盘安全校验只接受 Windows 与 Linux，其他平台会 fail closed，不能据此宣称已支持全部 POSIX 系统。
- **【修改原因】** 多个应用进程同时执行 `create_all`/`ALTER TABLE` 会发生重复列、部分迁移或启动失败；协调表尚未创建时不能先依赖数据库租约。
- **【影响范围】** 仅 `init_db` 的 SQLite 启动阶段。Prompt、Tool、Memory、Workflow、Context 和请求时延不变；非 SQLite 数据库继续依赖自身迁移设施。
- **【风险等级】** 中。数据库位于不受支持的共享文件系统时应拒绝协调部署，不能把 SQLite 网络盘当作多机数据库。
- **【验证方式】** 真实两个 OS 进程验证独占和释放；启动、旧库迁移与回执组合 36 项通过；完整后端回归覆盖增量迁移幂等和业务行保留。
- **【为什么这是最优方案】** 用标准库解决建表前的“先有协调表”循环依赖，不引入平台隔离、守护进程或第三方锁服务。

## 5. MCP SSE owner 路由

- **【修改内容】** 协调模式登记短期 SSE owner 路由；POST 若落到非 owner worker，则以稳定用户代次校验后写入加密邮箱，由 owner 解密并交给原 MCPServer。每会话邮箱有界，owner 死亡/未知或路由过期时要求重连；已断开的流不迁移。默认路径仍为原进程内队列。
- **【修改原因】** 负载均衡下 SSE GET 和后续 POST 可能落到不同 worker，原实现返回 session not found。
- **【影响范围】** MCP route/server、新增短期路由与消息表。JSON-RPC、Tool/Resource/Prompt 定义、确认、ACL 和响应只走原 SSE 的协议语义不变；邮箱内容加密，45 秒 owner 租期由活跃流续约。
- **【风险等级】** 高。邮箱提交 202 后 owner 随即死亡时流已丢失，客户端必须重连并检查业务回执，不能假装响应已迁移。
- **【验证方式】** 43 项 MCP 协议/权限测试通过；真实子进程 POST 到父进程 SSE owner，父进程收到 JSON-RPC 响应，数据库不含请求 ID 明文，错误用户被拒绝。
- **【为什么这是最优方案】** 保持既有 MCP 2024-11-05 HTTP+SSE 协议和本地执行模型，仅路由输入，不复制 SSE 输出或迁移运行中 Tool。

## 6. WebSocket 跨 worker 事件交付

- **【修改内容】** worker 只登记 execution_id/进程代次/订阅计数，不持久化订阅者 Token。发布者为其他订阅 worker 写入 60 秒、16 KiB 上限的加密事件；每目标最多 256 条并丢弃最旧遥测。接收 worker 解密后调用原本地广播，每个连接发送前继续重新认证并检查项目 ACL；路由事件不会再次发布形成环路。
- **【修改原因】** 执行 worker 与 WebSocket 连接 worker 不同会丢进度；共享订阅者 Token 或长期保存报告正文会扩大泄露面。
- **【影响范围】** WSManager 和短期事件/订阅表。前端协议、执行 Workflow、Prompt、Tool、Memory 和 Context 不变；事件总线只在 Coordinator 已注入时启动。
- **【风险等级】** 中。遥测是有界最佳努力交付，慢消费者可能丢最旧进度；最终执行状态仍以 DB/API 为准。
- **【验证方式】** 28 项 WebSocket、ACL、交付测试通过；真实子进程发布加密事件，父进程订阅者收到，数据库无消息明文；本地与路由广播均保持 ACL 复核。
- **【为什么这是最优方案】** 事件体短期加密、Token 保持进程内，并明确遥测与最终业务状态的职责，不引入常驻消息中间件。

## 8. 明确保留的架构边界

- **平台隔离：未实施。** 按用户决定，不加入 Windows Job、Linux cgroup 或容器强制隔离。
- **JMeter 执行跨进程接管/取消：未启用。** 没有可靠停止证明时，不释放可能仍在运行的压测资源，不把业务 COMPLETED 当作进程已停止。
- **自动恢复：未启用。** 未来请求的准备阶段恢复仍依赖可靠确认旧执行者停止、加密输入/保留配置、配置指纹和显式用户选择；在当前隔离与停止证明被推迟后，直接实现会有重复模型/Tool/归档风险。
- **多 worker 启动：未启用。** `main.py` 与部署脚本未注入 Coordinator。以上能力是可选原语与已验证切片，不是多 worker 上线声明。
- **协调平台范围：当前仅 Windows/Linux。** Windows 路径已有实测；Linux 文件系统校验和 `flock` 路径有代码/单测覆盖但未做本批真实部署验证；macOS/BSD 会被本地磁盘校验明确拒绝，需后续独立设计和验证，不能与本次“暂缓进程隔离”混为一项。
- **未验证外部系统：** 未运行真实 JMeter、Docker/容器、远程压测引擎、真实 LLM、真实 LanceDB 多进程写或网络文件系统，也未迁移用户数据库。

在这些边界下，本批扫描和测试未发现新增 Prompt、Tool Calling、Memory、Workflow 或 Context 回归；这不等于证明整个项目不存在任何 Bug。
