# Agent 第十一批续修与验证

本批承接“继续完成未完成的内容”，处理结构化提取、分析准备异常和自动假设评估的状态竞态。业务目标、Agent职责、Prompt语义、Tool schema及正常Workflow保持不变；不升级依赖、不修改表结构。修改前176个源码/配置/测试文件已在工作区外保存快照。

## 1. 补齐结构化假设缺失的服务端元数据

【修改内容】AnalysisAgent的直接JSON路径和模型提取路径统一使用解析函数。对于假设对象缺失的hypothesis_id、source_execution_id、module，分别提供空ID占位、当前Fact执行ID和模块；其余字段仍由原Pydantic模型校验。归档时仍使用原有确定性ID规则。

【修改原因】STRUCTURED_EXTRACTION_PROMPT要求模型输出陈述、类别、置信度、预测和证伪设计，但未要求生成上述三个必填字段。正常遵循Prompt的输出会因字段缺失被拒绝，回退到规则提取后可能丢失预测、证伪设计和原始评估；直接JSON路径还会多发一次模型请求。

【影响范围】AnalysisAgent结构化提取与后续RAGArchiver/HypothesisLedger输入。Prompt文本和Tool不变；Memory能保留原本已有的有效结构化内容，Context不再因这类解析失败丢失信息。显式给出的元数据不被静默改写，上一批归档来源冲突检查仍然生效。

【风险等级】低至中；优先级高。只补充缺失字段，不修正非法类别、置信度、列表结构或明确的null；不把模型陈述视为事实。返回结构化内容更完整，可能使原来丢失的假设进入既有未验证假设流程，这是恢复原有设计目标。

【验证方式】直接JSON/模型提取两条路径分别覆盖全部缺失和逐个缺失，共8项；验证陈述、置信度、依赖指标、预测及证伪设计保留，直接解析不发模型请求。5项非法内容与1项显式身份冲突测试保持既有拒绝/保留行为。

【为什么这是最优方案】这些标识由服务端已有Fact提供，无需让模型猜ID或增加Prompt字段；在解析边界补默认值，不放宽公共模型的必填约束，也不增加修复性模型重试。

## 2. 完整JSON代码块直接解析

【修改内容】直接解析和模型响应使用同一个围栏处理逻辑，支持完整的json、JSON和无语言代码块；只移除完整的外层围栏，仍要求整个内容是JSON对象。

【修改原因】旧直接路径不处理代码块，即使已经是可用JSON也会再次调用模型；模型响应路径只处理小写json开头，常见的无语言或大写JSON围栏会落入规则回退。

【影响范围】AnalysisAgent提取入口、模型调用次数和后续结构化数据。Prompt、Tool、Memory格式与Workflow步骤不变；不会从夹杂说明的正文中截出局部JSON冒充完整结果。

【风险等级】低；优先级中。只接受列出的完整围栏形式，不做任意文本中的JSON搜索、尾逗号修复或其他语言代码执行。不是通用Markdown解析器。

【验证方式】三类围栏×两条路径共6项，校验内容保留及模型调用次数；包括JSON字符串内部的三个反引号。另3项验证前后夹杂正文、非JSON语言围栏不会被静默截断接受。

【为什么这是最优方案】利用现有JSON解析器，在两个入口共用少量边界代码，减少确定无意义的模型调用；不新增依赖、不扩大宽松解析范围、不改变输出要求。

## 3. 分析Context准备失败可见且不继续执行

【修改内容】为来源scope读取、历史事实/假设读取、启发式和任务Context构造增加统一异常边界。向上传播的普通异常返回success=false、阶段及异常类型，保留已计算Fact；不向调用者回显底层异常原文。CancelledError继续传播。

【修改原因】原流程只处理Fact计算及分析后处理异常，中间准备阶段失败会直接抛出，调用者拿不到一致的失败返回与已计算事实。缺少scope时也不能把数据库错误当成可安全继续的空历史。

【影响范围】analyze_with_rag及两个便捷分析入口；失败发生在self.run之前，不调用模型、Tool或归档，不改变正常Prompt/Workflow。既有账本在内部捕获后返回空列表的读取错误仍属遗留边界，本批只处理实际传播到准备层的异常。

【风险等级】低至中；优先级高。错误响应不包含底层原文，但服务端仍保留异常日志；这不是全项目日志脱敏。不会在来源或上下文准备异常后自动降低隔离要求继续分析。

【验证方式】6个准备阶段各覆盖普通异常和取消，共12项；普通异常返回阶段错误及原Fact，取消向上传递，两者均不调用run、结构化提取或归档。既有scope筛选及正常后处理回归通过。

【为什么这是最优方案】在已有步骤之间补齐错误边界，保留当前失败返回风格与部分成果，不额外查询、不新增失败重试或引入新的异常处理中间层。

## 4. 自动评估跳过已处理或已废弃的假设

【修改内容】evaluate_against_facts读取假设后，只允许UNTESTED继续自动评估；CONFIRMED、REFUTED、DEPRECATED直接返回原记录，不读事实。

【修改原因】批量入口虽然查询UNTESTED，但查询与单条处理之间存在await，状态可能已经变化；单条方法本身原来也没有状态保护，可能重新确认、证伪甚至复活已废弃记录。

【影响范围】HypothesisLedger自动评估和AnalysisAgent分析后流程。保留原“评估未验证假设”的业务目标；Prompt格式和Tool不变，Memory中的已有验证决定不会在入口被无条件重算。已有显式update_status仍可修改状态，需要重新自动评估时可显式恢复UNTESTED。

【风险等级】低至中；优先级高。只在入口检查还不能解决评估过程中发生的变化，下一项同时补上写入时的保护。没有新增已确认假设自动持续重评策略。

【验证方式】三种非UNTESTED状态均验证记录完全不变，且在禁止事实读取的测试桩下返回。现有UNTESTED确认、证伪、自证拦截、scope及指标有效性测试全部回归。

【为什么这是最优方案】让单条入口遵守批量入口已经声明的范围，减少无效读取，不更改状态枚举、预测规则或因果验证边界。

## 5. 自动评估写入使用状态与更新时间条件

【修改内容】update_status增加可选expected_status、expected_updated_at关键字参数；自动评估提供读取时的值，SQL在同一UPDATE中比较。没有匹配记录时抛出专用HypothesisUpdateConflict；评估捕获后放弃旧判断并返回当前记录，不重试覆盖。未传条件的既有显式状态更新保持原行为。

【修改原因】仅在读取时检查状态不足以保护后续写入：读取事实或等待数据库期间，另一请求可能废弃假设、写入验证结果，甚至保持UNTESTED但更新说明。旧无条件UPDATE会覆盖这些较新的决定，两个自动评估也可能互相覆盖。

【影响范围】HypothesisLedger内的读写边界及上层评估返回。Memory的状态、验证来源、备注与更新时间共同保留；Prompt、Tool、Workflow不变。真正的写入失败仍返回false并由评估抛出失败，取消/回滚契约不变，不把数据库错误当作正常状态冲突。

【风险等级】中；优先级高。条件使用已有updated_at及其当前ISO保存格式，不是新增单调版本号。它不能识别绕过应用且未更新状态/时间戳的外部写入，也不保证跨存储一致性或按执行时间选出“最新”评估；并发评估保留首先成功写入的决定。

【验证方式】事实读取和实际写入等待两个边界，分别变更四种状态（含同状态UNTESTED备注更新），共8项；通过第二个账本连接验证旧评估不覆盖新决定。另1项让两个自动评估同时读取旧记录，确保后写者不覆盖先提交结果；6项既有写入失败、回滚、取消回归通过。

【为什么这是最优方案】使用现有表字段和SQLite条件UPDATE完成局部并发检查，不长时间持有锁读取/哈希JTL，不新建锁服务或迁移版本列；专用冲突结果与实际数据库故障分开处理。

## 后续方案：接通分析HTTP/SSE入口与Fact/RAG流程（已在第十二批完成）

用户已回复“是”确认此兼容方案。实现和最终验证见[第十二批报告](D:/trae/项目/jmeter-agent/docs/repairs/2026-08-28-twelfth-pass-fixes.md)。以下保留提出方案时的证据和权衡，不代表当前代码仍未接入。

### 提出方案时的证据

[通用Agent路由](D:/trae/项目/jmeter-agent/jmeter-agent-backend/app/api/routes.py:1280)在analysis分支创建AnalysisAgent，之后仍统一调用继承的run或run_stream，没有直接调用[专用分析流程](D:/trae/项目/jmeter-agent/jmeter-agent-backend/app/services/ai/agents/analysis_agent.py:160)。[请求/响应模型](D:/trae/项目/jmeter-agent/jmeter-agent-backend/app/models/schemas.py:384)也没有显式执行ID或Fact/validation/archive结果字段。

因此，本批验证的专用流程不能被描述为已在这两个HTTP入口完成端到端接入。通用工具仍能解析报告，执行完成后的TestAnalyzer也是另一条路径；这不等于所有现有报告功能都不可用。

### 推荐方案与影响范围

建议为analysis请求增加**可选的显式execution_id**，提供兼容入口：带ID时由服务端读取登记执行与其项目/计划上下文，走统一事实计算→分析→校验→归档流程；不带ID时保留现有通用任务行为，不从用户文本猜ID，不自动扩大文件访问或归档权限。

普通HTTP与SSE应共享这条编排流程，并协调Fact/归档回执、错误、取消和最终完成事件；不能在模型分析刚结束时就把尚未完成的归档宣告成功。相关影响包括请求/响应schema、AnalysisAgent编排、Session生命周期、SSE事件、客户端契约与集成测试。Tool权限、执行授权、未验证假设规则继续沿用。

### 利弊及推荐理由

- **收益：** 正式入口能够提供可验证的Fact与归档回执，减少通用对话与专用分析行为分离；调用者可明确知道分析、校验和归档各自是否成功。
- **成本/风险：** 需要同步处理响应兼容性、流式终止语义、取消期间部分成果和执行元数据来源，不能只替换一个方法调用。
- **不建议直接替换所有analysis任务：** 当前自由文本任务不一定有执行ID，强制要求会改变既有使用方式。
- **独立新增专用路由是可选方案：** 兼容边界更清晰，但会增加一套入口及调用方迁移。本次更推荐可选执行ID方案，保留现有任务模式，并让两种传输共享核心流程。

**本项已按确认方案实施并验证。** 第十二批增加69项后端和11项前端测试，兼容保留不带执行ID的行为；没有执行真实压测或调用付费模型。其他未完成边界仍保留。
