# Agent 第十批续修与验证

> 后续记录：本文件保留第十批结果。第十一批结构化提取、状态竞态修复及分析入口接入提案见[第十一批报告](D:/trae/项目/jmeter-agent/docs/repairs/2026-08-28-eleventh-pass-fixes.md)。

本批承接“继续完成未完成的内容”，处理账本与分析归档的异步数据一致性、来源冲突和重复写入。保持业务目标、Agent职责、执行授权与现有Workflow不变；不升级依赖、不修改表结构、不启动真实压测。修改前176个源码/配置/测试文件已在工作区外保存快照。

## 1. Fact写入使用同一份输入快照

【修改内容】FactLedger.save在首次await之前捕获索引字段、源路径、预期哈希、计算时间和嵌套JSON；后续哈希检查、SQL参数和失败日志使用这些值。使用绑定参数，不拼接数据到SQL。

【修改原因】旧实现跨初始化、文件哈希和连接等待多次读取可变FactSheet。调用方在等待期间修改对象，可能使保存的JSON与数据库索引字段不同，或把另一个路径/执行ID用于本次保存；后续读取可能找不到刚保存的事实。

【影响范围】FactLedger及其归档调用方。Memory保存边界变化，原有JTL哈希检查、事务回滚和取消传播保留。Prompt、Tool schema、Workflow步骤不变；历史Context不再受这种行内不一致污染。

【风险等级】低至中；优先级高。JSON序列化现在先于文件检查，源文件无效时可能多做一次序列化。快照针对同一事件循环中的异步交错，不构成跨线程锁或文件不可变保证；哈希检查后的文件变化仍由既有读取校验发现。

【验证方式】初始化、哈希、写入连接和提交四个边界注入调用方修改，检查主键、模块/版本/scope筛选、嵌套指标及raw_summary与入口值一致。提交阶段本来就安全的行为也保留；现有哈希失效、回滚和取消测试一并回归。

【为什么这是最优方案】提前生成原本就要落库的JSON和标量参数，不为整个Fact再做一次深复制，也不改变数据库模型、持久化格式或上层业务流程。

## 2. Hypothesis新增返回实际写入的ID

【修改内容】HypothesisLedger.add在首次await前固定ID和全部SQL参数，supporting_facts提前序列化；提交后返回捕获的ID，不再重新读取调用方对象。

【修改原因】旧实现不仅可能在等待时改写来源、陈述和依赖字段，还可能在INSERT完成、commit返回前对象被修改，最终返回一个从未写入的ID，造成归档回执失真。

【影响范围】HypothesisLedger新增入口和归档回执。已有ID和自动生成ID均支持；Memory字段、Prompt分组、Tool调用和Workflow不变。生成ID仍回填调用方对象，但时点提前到数据库初始化之前，因此初始化失败时对象也可能已经具有生成的ID。

【风险等级】低至中；优先级高。ID生成格式与失败后抛出异常的契约不变；返回ID代表本次成功提交/已存在条目，不意味着跨存储事务完成。未增加失败后的自动业务重试。

【验证方式】已有ID/空ID两种输入，分别在初始化、写入连接、提交阶段注入修改，共6种组合；确认返回值能读取到原始陈述、来源和嵌套依赖，调用方后来修改的ID没有被写入。

【为什么这是最优方案】把写入参数和返回回执绑定在同一个局部值上，继续使用现有事务，不冻结公共模型、不重构调用者，也不引入新的事务服务。

## 3. 一次分析归档固定事实与结构化分析

【修改内容】通过既有来源门槛后，在首次异步持久化前复制FactSheet和StructuredAnalysis；数字校验、假设归档、结论及原始报告投影都读取归档自己的副本。移除循环内已经多余的单条假设再次复制。

【修改原因】只修账本入口仍不足以保证整个归档过程一致：Fact保存后，调用方可能修改指标、分析列表、raw_summary或来源字段，导致校验使用另一版事实、已保存事实与派生报告不一致。

【影响范围】RAGArchiver、两个账本和分析后的派生知识。Memory/Context内容保持一次调用内一致；不修改Prompt、数字校验规则、Tool或Workflow，也不覆盖调用方在等待期间做出的后续修改。

【风险等级】中；优先级高。增加与输入结构大小相关的短期内存副本及复制成本；未据此宣称性能提升。它不是数据库快照隔离，不保证外部执行记录、文件和所有存储在整个调用期间都不变化。

【验证方式】在Fact保存和假设新增两个await边界修改原对象的执行ID、模块、版本、scope、p99、raw_summary、指标列表及假设内容。确认数字校验通过原始值，所有归档回执/投影使用同一来源和原始内容，调用方对象不被回写还原。

【为什么这是最优方案】归档确实跨多个await使用这些嵌套字段，入口副本能在单一责任边界解决问题；账本层只序列化必要参数，避免叠加第二份完整Fact深复制。不改全局模型可变性或存储架构。

## 4. 拒绝与事实来源冲突的分析元数据

【修改内容】Fact成功保存后，检查StructuredAnalysis中的非空execution_id、module、version是否与Fact一致。冲突时保留Fact回执，停止假设、结论和raw_report派生归档，返回rejected_reason及errors；缺失或空元数据沿用既有兼容行为。

【修改原因】旧归档直接用Fact来源重标记模型分析，可能把明确属于另一执行/模块/版本的内容存到当前执行下。单纯改写标签无法证明内容对应当前事实。

【影响范围】结构化提取结果、RAGArchiver及AnalysisAgent既有后处理错误汇总。无需修改Prompt或Tool；正常Workflow不增加步骤。错误分析不进入长期知识，确定性Fact仍保留；基于已保存Fact的独立历史假设评估沿用既有流程。

【风险等级】中；优先级高。模型若生成错误来源，分析后处理现在会显示失败，而不是静默接受。比较为精确匹配，不猜测版本别名；空字段兼容并不等于证明来源真实性，完整证据映射仍未完成。

【验证方式】分别注入执行ID、模块、版本冲突，确认Fact只保存一次、所有派生写入均未调用且错误可见；缺失、空值和完全匹配三条正常路径通过。AnalysisAgent原有后处理失败与部分结果保留测试全量通过。

【为什么这是最优方案】在最终归档边界检查，不仅依赖模型遵循Prompt；拒绝明确矛盾的数据，同时保留独立计算的Fact和既有缺失字段兼容性，不让模型重试浪费Token。

## 5. 假设重复归档改为数据库原子去重

【修改内容】HypothesisLedger.add新增仅关键字参数if_absent，默认false保持普通INSERT行为。归档显式启用后，只对hypothesis_id冲突执行DO NOTHING；移除归档中的先get再add。确定性ID算法不变，已有行内容、时间和验证状态不被替换。

【修改原因】两个归档任务可能同时查到“没有该假设”，随后第二次INSERT因主键冲突失败。实际上记录已经存在，却向AnalysisAgent返回归档错误；先查再写也多一次查询和初始化入口。

【影响范围】RAGArchiver与HypothesisLedger两个模块同步修改。普通新增仍拒绝重复ID；其他约束和数据库异常沿用回滚/抛出处理。Memory去重语义保持“已有条目优先”，不增加Tool、LLM调用或Workflow重试。

【风险等级】低至中；优先级高。仅保证单张SQLite表、同一确定性ID的原子去重，不代表整个RAG跨存储原子性或工具exactly-once。重复调用仍提交一次无更新INSERT尝试，不能把减少一次get等同于所有负载下吞吐更高；首次记录优先也不会自动合并后来变化的置信度/预测。

【验证方式】旧源码下强制两个归档在插入前都读到空，复现UNIQUE失败；修复后并发回执一致、库内一条记录且不调用get。两独立账本连接并发插入同一临时SQLite也通过；重归档保留确认状态、验证来源和备注；普通重复INSERT及NOT NULL约束仍报错。

【为什么这是最优方案】由已有主键约束完成去重，使用定向ON CONFLICT而非吞掉所有约束错误；不靠进程内锁掩盖竞态，不引入重试循环、幂等日志或新存储组件。

- **高：真实执行与隔离验收。** 需授权测试目标、负载上限、容器/远程环境。推荐专用服务验证生成→执行→取消→报告归属；能覆盖操作系统边界，但需要环境和压测授权。
- **高：出站策略及报告origin。** 影响URL/DNS/代理、认证和前端报告链接。推荐依据部署拓扑明确白名单及独立报告域名；能限制访问与脚本暴露，代价是部署和私网兼容设置。
